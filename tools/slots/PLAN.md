# 色块入槽辅助 · 实现方案

> 状态：**已实现**（2026-11-22）。基于实机探索（小米 2209129SC / 1080×2400 / 京东 Manto 小游戏「关卡92」）。
> 实机验证：`quick.sh --once` / `--dry-run` 正常；默认模式跑通「2 次广告解锁 + 3 次点击」，89 秒无异常；复活弹窗命中即抛异常停手（不点击）。
> 目标：用现有 `adb 抓图 → 视觉识别 → 规则决策 → adb 点击` 工具链，自动执行「点底部第一排色块 → 入槽收集同色」循环。
> 本文件只描述方案，不含实现代码。

---

## 一、用户规则（权威）

1. 点击**底部第一排**色块，色块进入中部槽位并开始收集同色目标。
2. 有的槽位/区域带「解锁」字样和摄像头图标，点击后看广告解锁。
3. 决策简化为：**优先选第一排中颜色不在中部槽位里的色块**；若第一排所有颜色都已被槽位占用，则**随机点一个第一排色块**。
4. 游戏中可能出现弹窗；**复活弹窗优先级最高，命中立即结束任务，不做任何操作**。

### 受控实验（已做，均只点 1 次）

1. 初始：槽位仅有绿色 22；第一排为 粉29 / 蓝36 / 红33 / 绿33 / 蓝36。
2. 点粉色 29 @(150,1900)：第一排整体左移补位；槽位短暂出现粉色 20，约 4~6 秒后清除，棋盘底部对应粉色 dangling 块被收走 → **槽位状态是动态的，必须等画面稳定再判定**。
3. 点绿色 32 @(150,1900)（槽位已有绿色 22）：**没有合并**，而是新开一个绿色槽（32 与 22 并存）→ 印证「同色已在槽中就别再点」的规则。
4. 点左侧「解锁」@(110,1500)：直接跳京东广告信息流（无确认框）。控件树含 `text="点击立即返回"`，bounds `[880,663][1045,698]`；点击后回到游戏，**左侧解锁按钮消失**（解锁成功）。右侧仍可再解锁一次。
5. 后续出现复活弹窗（`outputs/shot_revive.png`）：顶部「关卡已完成: 27.0%」+ 提示「放置栏已满」，弹窗标题为橙底黄色「复活」，下方绿色「复活」广告按钮 + 红色 ×，文案「复活后将增加槽位」。用户要求此时**立即停手、不点任何东西**。

### 颜色阈值 → 已由马赛克拼图标定为完整颜色池（见第六节）

早期只按 H 粗分（红~0 绿~63 蓝~118 粉~165）。现已在关卡93马赛克拼图完整画板上精确标定出 **14 色调色板**（含新增玫红/浅紫分辨），并据此重写 `hue_name`，详见第十节与 `palette.json`。

## 三、可行性结论

**可行，且比 parking/ring 更简单。** 色块是固定网格里的纯色圆角矩形，不需要车辆箭头、OBB、等距投影或阻挡射线判定；感知层只做「第一排色块颜色 + 槽位占用颜色 + 解锁按钮 + 复活弹窗」。

- 广告解锁、返回游戏、安全验证暂停、点击/等待/通知等执行层逻辑，**可直接照搬 `tools/ring/ring_auto.py`**（`dump_ui` / `find_text_node` / `watch_ad_return` / `wait_for_user` / `wait_stable` / `notify_phone`，`unlock_all_docks` 稍作适配）。
- `grab` / `hue_name` / 连通域检测 / 模板匹配 / `annotate` 可照搬 `tools/ring/ring_vision.py` 的结构。
- 新增工作集中在：**两组 ROI 的色块检测、解锁按钮模板、决策循环**。

风险不在可行性，而在「动画期间抓图」和「复活模板是否通用」。

## 五、感知层方案

1. **抓图**：`adb exec-out screencap -p`，与 ring 一致；比例化坐标以 1080×2400 为基准。
2. **第一排检测** `detect_first_row(img)`
   - ROI：`y=1810~2000`，全宽；HSV `S>90 & V>90`，闭运算后连通域。
   - 过滤 `area>1500, 120<w<240, 90<h<190`；取质心 + 中位色相，用 `ring_vision.hue_name` 映射为 粉/蓝/红/绿/黄/青/深红；近黑归 `black`。
   - 按 x 排序，返回 `{x, y, box, color}`。抓不到时视为动画中，等待重试。
3. **槽位检测** `detect_slots(img)`
   - ROI：`y=1610~1760`，按 5 个 x 窗口（中心 103/310/517/724/931，半宽 100）切分。
   - 窗口内高饱和像素占比 > 25% 视为占用，取中位色相 → 颜色集合 `slot_colors`；否则为空。
   - **只取颜色集合参与决策，不依赖数字**（数字是动态进度，识别意义不大）。
4. **解锁按钮检测** `detect_unlock_buttons(img)`
   - 左/右两个固定搜索区，用 `unlock.png` 做 `TM_CCOEFF_NORMED`，阈值 0.85，NMS 去重。
   - 实测解锁后对应按钮消失，因此可循环「找第一个 → 点 → 看广告返回 → 再找」直到没有。
5. **复活弹窗** `detect_revive_dialog(img)`：用本游戏模板 `tools/slots/templates/revive_banner.png`（从实机截图裁 y=650..730 / x=435..650，橙底黄色「复活」标题），阈值 0.8。实测本图自匹配 **1.000**，普通关卡画面最高 **0.543**（ring 紫模板 0.316、dogs 橙模板 0.386），区分度足够。
6. **胜利界面** `detect_victory_dialog(img)`：用本游戏模板 `tools/slots/templates/victory_banner.png`（从 `outputs/shot_victory.png` 裁 y=510..690 / x=195..885，橙底黄字「挑战成功」标题；与复活横幅同美术风格但文字不同），阈值 0.8。实测胜利图自匹配 **1.000**，普通关卡 0.216、复活弹窗 0.213，互不误判。用户定稿：命中立即停手、不做任何点击。

复活与胜利统一为终止状态：`slots_auto.guard_terminal()` 在每个抓图点优先检测两者之一，命中抛 `TerminalState`，由主循环捕获后停止任务（不做点击/关弹窗）。
6. **其它弹窗**：先复用 ring 的「助力礼包」× 检测（且必须先排除解锁确认框/复活弹窗）；未识别的浮层一律停止并通知，避免对着弹窗盲点。
7. **标注图**：绿色粗框 + 黄底大号「1」标本轮要点的块；其它第一排块用蓝色圈号；槽位颜色用大号文字标出；解锁按钮画虚线框。沿用现有醒目风格，方便肉眼核对。

## 六、决策层方案

### 主循环（每轮）

```
抓图
  → 复活弹窗？ 是 → 停（不点任何东西）
  → 广告页/安全验证？ → 走 watch_ad_return / wait_for_user
  → 有解锁按钮？ → 解锁一次（看广告 → 返回 → 复查）
  → wait_stable 等画面稳定（min 0.6s / max 6s / 相邻帧差 <0.012）
  → detect_first_row + detect_slots
  → 选块：
       cand = 第一排中 color ∉ slot_colors 的块
       若 cand 非空 → 取最左一个（早期方案；现按首次出现顺序、同色多块随机选，见第九/十节）
       否则 → random.choice(第一排)（用户定稿的兜底）
  → adb shell input tap (x, y)
  → 等稳定，校验第一排是否变化；无变化累计 no_effect_streak
```

### 兜底与停止条件

- 第一排连续 N 帧（默认 3）识别不到 → 停止并通知（可能已通关/弹窗）。
- 连续 5 次点击后第一排无变化 → 停止（避免对着动画/浮层空点）。
- 近期点击过的坐标 2 秒内不重复选（防同一位置连点）。
- `--max-clicks` / `--max-seconds` 到限停止；`Ctrl+C` 可随时中断。
- 结束手机通知复用 `ring_auto.notify_phone`（标题「色块入槽」）。

### 尚待确认（不阻塞方案评审）

1. 是否每局都把左右两个解锁都看广告解锁（默认：**是，各一次**）？
2. 通关结算弹窗要不要单独做模板识别（目前只靠「第一排消失 + 无响应」间接判断）？
3. 非复活的未知弹窗：默认**停止并通知**，还是尝试自动关闭？
4. 目标是单关还是连续刷关（默认：**单关**，与 ring 一致）？

## 九、已修 Bug（2026-11-22）

**现象**：第一排明明有不在槽位中的颜色，工具仍点了重复颜色。

**根因**：旧 `pick_block` 用「近期点击过的坐标」排除候选（2 秒冷却）。第一排补位后仍落在**相同 x 坐标**，若循环较快，唯一的非重复色块恰好在刚点过的列上，就会被冷却误排除，于是 `fresh` 为空 → 走随机分支点了重复色。

**修复**：
1. 坐标冷却只用于「点击无响应」的块（连续无响应时才屏蔽该坐标 2 秒），成功后立刻清空，不再屏蔽正常点击后的补位块。
2. `detect_slots` 改为固定槽位窗口的高饱和像素占比判定（阈值 0.20），替代严格连通域面积/尺寸过滤，动画/白色数字把色块分割开时也能识别占用。
3. 决策日志增加「候选: 第一排=... 槽位=...」，方便肉眼核对。

**验证**：修复后实机 `--no-unlock --max-clicks 5`，5 步分别选 红/粉/绿/蓝/红，每步都避开当时槽位颜色，无重复误选。

### 黑色块漏检（同日补修）

**现象**：当前第一排有 4 个黑色块，工具却只识别到 1 个橙红块，因而选了已在槽位中的红/橙色，没选黑色。

**根因**：`detect_color_blocks` 的掩码只收 `S>90 & V>90` 的高饱和像素；黑色块实测 `H≈135 / S≈31 / V≈42`，整块被过滤。`detect_slots` 同样只认高饱和像素，黑块进槽后也会漏判。

**修复**：两处掩码都加上暗色分支 `(V<110 & S<90)`；颜色统计对应放宽，低亮度低饱和归为 `black`（`slots_vision.hue_name` 已有该分支）。

**验证**：当前画面识别为 `黑/黑/黑/黑/红`，槽位 `绿/粉/红`；`--dry-run` 正确选中黑 `@(149,1904)`。历史截图回归结果不变。

### 批量决策 → 简化为「一轮顺序点击」（同日定稿）

**需求演进**：先要求一次决策选多个不同色块减少等待；用户随后明确**色块「点不动」是互相捆绑所致，该机制先不处理**——只需按顺序点不重复色块，点完一轮再重新决策。

**根因澄清**：之前批内出现的「无响应」并非识别/坐标问题，而是第一排色块被上方其它块**捆绑**导致无法移动（用户确认）。既然该机制暂不处理，围绕它设计的「无响应累计停止 / 坐标冷却屏蔽 / 点掉一块后续左移的列偏移预测」都属于多余复杂度，已全部删除。

**最终实现**：
- `pick_batch(result, args)`：按第一排首次出现顺序取「颜色不在槽位、彼此不重复」的块，**同一颜色有多个块时随机选一个坐标**（避免总点最左那块）；最多 `--batch-size`（默认 3；`0`=全选）；全部占用时退回随机单块。不做容量预留——占满触发的复活弹窗由最高优先级分支兜底停手。
- 点击阶段：按决策时记录的**原坐标**顺序点完这一批，两次间隔 `--batch-gap`（默认 0.45s）。**不判断是否有响应、不屏蔽坐标、不预测补位左移**——因为色块补位后仍落在相同 x 列，不存在整体左移。
- 整批结束后只做一次 `wait_stable`，重新抓图进入下一轮决策。
- 标注图支持多块编号 1..N。

**验证（实机 2026-11-22）**：
- `--dry-run`：第一排 `红/橙粉/粉/白/红`、槽位 `绿/粉` → 选 `红/橙粉/白`（避开粉、两个红去重），标注 1/2/3 正确。
- `--no-unlock --max-clicks 6` 跑两轮：第 1 轮点 红(145)/橙粉(340)/白(730)，第 2 轮重新抓图后第一排变为 `红/青/粉/橙粉/红`，点 红(145)/青(340)/橙粉(730)。补位后仍是固定列，列偏移预测确属多余；全程未按「无响应」提前停止。
- 单元验证：`红/红/黑/绿/粉` 场景，槽含红→选 黑/绿/粉；空槽→选 红/黑/绿（去重）；全占用→随机单块；`batch-size=0`→选全部 4 个不同色。

## 十、颜色池标定（2026-11-22，关卡93 马赛克拼图）

用户要求补全颜色池，颜色从马赛克拼图的小色块获取，并仔细分辨相近色。马赛克目标图每格是纯色填充，是天然的颜色标定板。

### 标定方法（可复用）

`tools/slots/palette_calibrate.py`：Sobel 投影 + FFT 估网格步长（实测 ~20px）→ 逐格取内部众数色（避开描边/高光点）→ KMeans(K=14) 聚类 → 输出每色 RGB/HSV/占比 + 建议分类到 `palette.json`。

```bash
tools/slots/palette_calibrate.py --device <serial>            # 实时抓图标定
tools/slots/palette_calibrate.py --image outputs/shot_mosaic_recheck.png  # 用截图标定
# 换关卡网格对不齐时用 --ox/--oy 微调格心偏移（默认 6/16，使 x≡16 mod 20）
```

### 相近色分辨规则（`hue_name` 已按此重写）

- **黑白灰先于色相**：近黑 `V<70`（S 可高达 180+）；白收紧到 `S<20 且 V>232`，否则浅蓝灰(S≈43 V≈236)会被旧白判据(S<45&V>232)抢走。低饱和 `S<75` 中先挑浅紫(H123~147 且 S>=40 且 V>180→`lavender`)，其余按 V 分浅蓝灰(>202)/中灰(>=140)/深灰(<140)。

- **粉 vs 玫红**：粉 H166 S126、玫红 H176 S210，靠色相带(150~167 vs >=170) + 饱和度区分。
- **紫 vs 蓝 vs 粉**：紫 H125~149 从 blue 中独立；浅紫 H123~147 低饱和单独归 `lavender`。

## 十·再补、2026-11-22 第一排灰白块漏检

**现象**：关卡93 当前画面第一排是 `白36/黑33/白35/黄29/白36`，工具只识别到 `黑/黄`，白色块完全消失，因此不会优先选白。

- `hue_name` 白色判据 `S<20 & V>232`：即便检测到也会被判成 `gray_light`；
- `detect_slots` 白块分支同样 `V>232`。

**关键区分数据**（同一张截图实测）：

| 区域 | 中位 S | 中位 V | S<10&V>210 | S<45&V>210 |

| 第一排灰白块 | 0 | 221 | 0.73 | 0.73 |

## 十一、风险与边界

- **终止态模板已实拍**（2026-11-22）：`revive_banner.png`（复活）、`victory_banner.png`（挑战成功），普通画面误报距离足够；若后续改版换新样式需重拍。

- **合规**：仅模拟点击，不修改游戏数据、不绕过付费；账号风控由用户自行判断。
