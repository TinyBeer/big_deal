### 已澄清（原待验证项，用户确认）
- 接客判定：**只有队首乘客能上车**，装满后车开走、接驳位释放；愤怒（接不到）没有后果。

### 实现阶段实测结论（2026-11-20）
- **队首 = 队列最左端**（实控实验：点绿车后最左绿色乘客被接走、队首变蓝），`--head-side left` 已定为默认值。
- 车开出后到达任意空接驳位即可；愤怒无后果、接驳位充足，按「有空位即可」处理。
- **开局解锁全部接驳位已跑通**：模板匹配找「解锁」位 → 点 → 看广告 → 点「点击立即返回」→ 回对局，实测 2 个位全部解锁为 P 位。
- 识别现状：约 48 辆车/帧，队列头部按颜色段切分识别稳定。

### 三项关键改进（2026-11-20 二轮实测落地）

1. **方向识别改为「箭头模板匹配」**（替代原白色质心法，彻底修掉 ↓ 车判反）
   - 四个方向箭头大小/颜色完全一致，仅旋转不同 → 全图检测**纯白箭头连通块**（V>235、S<50，约 65×23 横 / 26×55 竖，面积 200~2000），按位置归属到车辆。
   - 朝向判定用**箭头三角头宽度**：沿主轴把箭头分两半，三角端横向跨度明显更大。实测深红/青两辆 ↓ 车由误判 ↑ 修正为正确的 `down`，跨度对比悬殊（如 up=25 vs 5、down=5 vs 25）。
   - 灰色障碍车无箭头，正好被排除，不再误判为车。

2. **阻挡判定改为「二维坐标系全程射线扫描」**（替代原「附近 bbox 相交」）
   - 沿箭头方向从车头到棋盘边缘建一条射线走廊，检查**整条路径上所有占用块**（棋盘车 + 停在接驳位的车）是否与走廊相交；不再只看相邻车。
   - 把接驳区车辆纳入占用计算，避免误判「能开出」导致接驳位满后开车的失败态。

3. **接驳区仅剩 1 空位即停**（避免误入广告/复活弹窗）
   - 模板匹配数**空 P 位**（`templates/p_slot.png`，实测 3/5 个空位与肉眼一致）。
   - 主循环每步检查 `len(empty_slots) <= --min-empty-slots`（默认 1）即停止，连续确认帧数 `--slot-confirm` 默认 1（**剩 1 立即停**，不再多点一步触发失败），停止原因写进结束通知。

### 8 方向 / 等距投影倾斜关卡（2026-11-21 三轮实测落地）

**现象**：部分关卡车沿斜线开出，工具把所有斜箭头判成 left/right，可开出只剩 1 辆、反复点同一辆卡死。

**根因（数据验证）**：
- 游戏画面是 **2:1 等距投影**。世界坐标里棋盘正交、车沿 8 方向（4 正交 + 4 对角）行驶；投影到屏幕后，45° 斜向被压成 `arctan(1/2)=26.565°`。实测箭头长轴 25.3°/151.9°、夹角 126.57°，与理论 26.565°/153.435°/126.87° 精确吻合。
- 8 个世界方向 → 屏幕上 **4 条轴 × 2 朝向**：水平 0° / 垂直 90° / 斜 26.565° / 斜 153.435°（历史"正交"关卡实测在 15°/165°、75°/105°，只是未超 bbox 翻转临界 `arctan(24/67)≈19.7°` 才侥幸能用）。
- 旧 `detect_arrows` 用 bbox 宽高比分横竖：26.6° 时箭头 AABB 恒为"横"，全部误判成 left/right。

**实现**：
1. **箭头改 minAreaRect 主轴角度 + 三角头定正反** → 8 方向名（含 ↖↗↙↘）与单位向量 `vec`。每辆车带 `axis`/`vec`，`detect_direction` 按位置归属箭头。
2. **车身加 OBB**（连通域原始像素 minAreaRect），供几何射线用。
3. **可开出判定 = 几何法 AND 像素法**：
   - 几何法：沿 `vec` 用 OBB 投影检查占用块（含接驳车）；
   - 像素法：沿 `vec` 在棋盘内采样，检测异色车漆/灰障碍连续段，出棋盘即畅通；
   - 取交集偏保守——宁可漏一两辆可开车，也不把被挡的车判为可开出导致点击卡死（核心痛点）。实测漏检的绿车@(742,1135) 由像素法正确拦下。
4. **点击点改为像素验证**：`pick_tap_point` 在车身内取多个候选（中心优先，沿车身轴/垂直偏移），选 HSV 匹配本车色的实心车漆点；实测 27/27 辆车 tap 全落车漆上。
5. 标注图加紫色方向箭头线，便于肉眼核对朝向。

**实测**：倾斜关卡方向识别与车身箭头完全吻合（↖↗↙↘），可开出从误判的 1 辆恢复到 5~11 辆；真实测试车数持续下降、队首变化正常、不再反复点同一辆；剩 1 空位准时停手。

### 倾斜关卡处理策略（用户定稿 2026-11-21）

- **规则变更**：8 方向/倾斜关卡不要求工具自动打。开局照常看广告解锁全部接驳位，**解锁后立刻停手**并通知，由用户手动接手（点击 0 次）。
- **判定**：`parking_vision.tilt_info()` 只统计「方向名为 ↖↗↙↘」且「箭头主轴角贴近 26.565° / 153.435°（容差 8°）」的块。实机斜关轴角 26.0~28.4° / 151.6~152.8°，旧正交关约 10°/75°/168°，不会误报。
- **执行**：`parking_auto.auto_run()` 在解锁阶段后抓稳定图分析，命中即设置停止原因、跳过决策循环并沿用原结束通知；识别不到棋盘（3 次重试）时跳过检测、按原流程继续，不阻断开局。
- **覆盖开关**：`--allow-tilted` 可显式恢复倾斜关卡自动接客（保留原 8 方向能力，方便日后改主意）；默认关闭。
- `--dry-run` 下同样会显示停手原因，但不会点击或发通知。

### 仍保留的兜底机制
- 点击后**验证车数/队首是否变化**，无响应记入失败列表并**换另一辆可开车**；连续无响应达上限（默认 6 次）自动停止。
- 残局大量车互相堵死时进展变慢，属局面结构性限制（非 bug）；无同色可开车时策略为「点任意可开车疏通」。

## 二、可行性结论

**可行，且与现有工具链高度同构。** 本游戏本质仍是「adb 抓图 → 视觉识别 → 规则决策 → adb 点击 → 等画面稳定」的闭环，和 `tools/spool/`、`tools/dogs/` 完全同型：

- 广告解锁 / 返回流程可 **直接复用** 两工具的 `dump_ui + 找『立即返回』+ tap` 与 `uiautomator` 方案；
- 安全验证暂停等人操作、结束发手机通知，也可复用；
- 新增工作量集中在三块：**网格标定、车辆/箭头识别、可开出与接客决策**。

风险不在「能不能做」，而在「识别稳不稳」和「决策会不会把局面玩死」。

## 三、技术架构

沿用统一约定：Python venv 在 `tools/requirements.txt`（numpy / Pillow / scipy / opencv-headless），入口 `tools/parking/quick.sh`，产物统一写 `outputs/`。建议拆成四个模块：

```
tools/parking/
  quick.sh            统一入口（--once / --auto / --dry-run / --image）
  calibrate.py        网格标定：从截图确定行列中心 → outputs/parking_grid.json
  parking_vision.py   抓图 + 识别（车/箭头/颜色/队列/P位） + 标注输出
  parking_auto.py     决策 + 点击 + 广告解锁 + 通知（复用 spool/dogs 的公共逻辑）
  templates/          箭头方向、解锁图标、愤怒脸、道具等小模板
outputs/
  parking_grid.json   标定结果（一次标定，跨局复用）
  parking_annotated.png 每轮标注图
```

标注图沿用醒目风格：绿色粗框 = 本轮要点的车，黄底高亮 + 大号「1」；其他可开出的车用蓝色圈号。

## 四、感知层方案

### 1. 网格标定（关键前置）
- 棋盘区域约 `x=40~1040, y=990~1810`（1080×2400 图上），横车/竖车交错排列。
- 参考连连看 `llk_calibrate.py` 的思路：**一次标定**确定每格中心坐标，存 `outputs/parking_grid.json`，跨关卡复用；不同布局再单独标定。
- 需要区分「一格一车」的粗网格还是「横车占2细格」的细网格，标定时由人工确认。

### 2. 车辆识别（每格）
- **颜色**：取车身中心区域主色，HSV 阈值分类为 红/黄/蓝/绿/青/粉/深红；灰黑「?」归为障碍。
- **方向**：车头白色箭头是稳定特征，用四方向小模板匹配（←→↑↓）；也可用车身长宽比先判横/竖再二选一，减少误匹配。
- **占用**：记录每格是「空 / 车(颜色,方向) / 障碍」。

### 3. 乘客队列识别
- 顶部一排小人 `y≈550~610` + 右侧竖列彩色圆球，按 x（和竖直方向）顺序读颜色序列。
- 「排队人数」数字区可用 OCR 或模板数字识别，用于判断通关/进度（可选）。

### 4. 接驳位状态识别
- 扫描中部 P 位行：识别虚线 P（空位）与「解锁」图标（未解锁），统计可用接驳位数量。
- 是否需要识别「被车占用的 P 位」取决于待验证项 2。

## 五、决策层方案

### 1. 可开出判定（核心规则）
对每辆车，从车头沿箭头方向逐格扫描至出棋盘：
- 途中任意格有车或障碍 → **不可开出**；
- 全程畅通 → **可开出**，记录其目的地为接驳位。

### 2. 接客匹配（核心）
- **只有队首乘客能上车**。因此只考虑「可开出」且「颜色 == 队首颜色」的车。
- 队首颜色从顶部乘客队列识别（左端/右端由标定实验确认）。
- 愤怒无后果：若没有同色可开出的车，点任意可开出的车疏通（会愤怒但不惩罚），让局面继续流动。

### 3. 选车优先级（定稿）
1. 可开出 + 颜色 == 队首颜色 → 立即点（真正接客）。
2. 无可开出的同色车 → 点任意「可开出」的车做疏通（无惩罚，为同色车让路）。
3. 没有任何可开出的车 → 停止并通知用户（不使用道具）。
- 接驳位不足时：因开局已全部解锁 + 车装满会释放，正常不会不足；兜底仍可再看广告解锁。

### 4. 卡死/异常
- 连续 N 轮无可操作项 → 判定卡死，发通知退出。
- 识别置信度低的格子标为「未知」，决策时保守跳过。

## 六、执行层方案

- **点击**：游戏内用 `adb shell input tap`；弹窗浮层用 `input touchscreen tap`（沿用狗狗工具的经验，两者对 canvas/浮层有效性不同）。
- **节奏**：点击后等画面稳定（`-wait/-max-wait` 可配），避免动画期间抓图误判。
- **开局解锁**：进入对局后先扫描接驳位行，逐个点「解锁」位 → 广告 → 「点击立即返回」→ 回到对局，直到没有解锁位（最多 3~4 个）。解锁完再开始正常决策循环。
- **广告解锁（兜底）**：点解锁位 → 检测跳到广告页 → 循环 dump 控件树找「点击立即返回」→ tap → 用画面均值/棋盘特征判断是否回到对局；复用 `watch_ad_return`。
- **安全验证**：检测到「安全验证 / 京东验证」暂停，等用户手动完成再继续（复用 `wait_for_user`）。
- **结束通知**：复用 AutoJS6 状态栏通知（标题如「停车场接客」）。
- **参数风格**：`--dry-run` 只演示第一步不点击；`--max-clicks`、`--max-seconds`、`--no-unlock`、`--security-timeout`、`--no-notify` 等与现有工具保持一致。

## 九、风险与边界

- **识别稳定性**：灰车「?」、半遮挡车、颜色相近（青/蓝、粉/红）易误判，需要模板 + 颜色双重校验。
- **不可逆操作**：盲目开出接不到客的车可能占死接驳位，决策宁保守勿激进。
- **广告依赖**：解锁位靠广告，平台改版会破坏返回流程，需保留人工兜底。
- **合规**：仅用于个人娱乐辅助，不修改游戏数据、不绕过付费，仅模拟点击。
